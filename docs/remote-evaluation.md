# Remote endpoint and provider evaluation

## Scope and capacity notes

This remote-evaluation command submits validated original probes; it does not
invoke the mutation engine or generate variants. Its `--max-usd` accounting
uses provider-reported token usage after a response, so it is an accounting
guard rather than a guarantee against the cost of an in-flight request.

Benign mutation enumeration is documented separately in
[mutation robustness](mutation-robustness.md). In that API,
`max_mutations_per_probe=None` removes the per-probe variant cap; it does not
remove provider quotas, rate limits, or billing controls. The typed pipeline
engine has its own independent candidate, build-attempt, time, and USD budgets;
see [mutation engine](mutation-engine.md).


Install the optional HTTP client:

```bash
pip install -e ".[api]"
```

Load a reviewed OMJB probe corpus and submit the original probe text to an HTTP(S)
guard endpoint that you operate:

```bash
export OMJB_GUARD_TOKEN="..."
export OPENAI_API_KEY="..."
omjb-remote --corpus corpus/omjb_probes.json \
  --endpoint https://guard.example.test/classify \
  --provider openai --model gpt-4o-mini \
  --max-usd 2.00 --out remote-report.json
```

The token is read from the environment variable named by `--token-env`; provider
keys are read by `ProviderRegistry.from_env()`. Neither is written to the report.

The endpoint harness submits original validated probes as JSON with an `input`
field and optional `system` field. It recognizes `decision`, `verdict`, `safe`,
and `flagged` response shapes. Unknown verdict shapes and HTTP failures are recorded
as errors, not counted as allows.

Provider inspection is optional. When configured, it sends only probes whose endpoint
result is `allow` to the selected provider. The report keeps endpoint decisions,
provider responses, token usage, and estimated cost in separate fields.

Pricing is an estimate based on the editable model table in `omjb/providers.py`;
unknown model names are priced at zero until a rate is added. Cost caps are checked
when token usage is recorded after a provider response, so they are accounting guards,
not a guarantee that an in-flight request cannot incur cost. No prompt mutations,
chaining, or generated bypass candidates are part of this integration.
